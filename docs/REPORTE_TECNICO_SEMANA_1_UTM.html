1. Entregable Parcial 1: Fase de Diagnóstico y Selección Arquitectónica

1.1. Análisis de Requerimientos de la Problemática

El proyecto responde a la necesidad operativa de una empresa de servicios técnicos especializada en mantenimiento electromecánico y agrícola. Las cuadrillas de técnicos son enviadas a zonas rurales, pozos de extracción y comunidades de difícil acceso geográfico donde se presentan las siguientes restricciones críticas:

  • Zonas Blancas (Cero Conectividad): Durante la mayor parte de la jornada laboral en campo no existe señal de red celular (ni 4G/5G ni GPRS) ni redes Wi-Fi disponibles. La solución debe permitir levantar reportes técnicos, diagnósticos y fallas de manera 100% autónoma y offline.
  • Heterogeneidad de Dispositivos (BYOD - Bring Your Own Device): Los técnicos utilizan sus propios teléfonos inteligentes de diversas gamas (baja, media y alta) con sistemas operativos mixtos: smartphones Android (motores Chromium/Blink) y teléfonos Apple iPhone (motor WebKit/Safari).
  • Recursos de Hardware Limitados: Muchos de los equipos en campo disponen de poco espacio de almacenamiento disponible y memoria RAM moderada, por lo que una aplicación pesada (mayor a 40 MB) genera rechazo e imposibilidad de instalación.
  • Costo y Tiempo de Despliegue: La empresa requiere una solución ágil que no implique pagar licencias anuales de tiendas ($99 USD en Apple Developer Program) ni atravesar semanas de aprobación burocrática por cada actualización o ajuste al formulario de campo.

1.2. Análisis Comparativo de Alternativas Arquitectónicas

Se analizaron las cinco opciones de arquitectura de software frente a los requerimientos de campo:

Arquitectura Comportamiento en Zona Rural Ventajas Principales Desventajas / Inviabilidad en Campo
1. Web Tradicional (SSR / MPA) ❌ Falla total Bajo costo inicial, actualizaciones instantáneas en servidor. Requiere conexión HTTP síncrona en cada clic. Al no haber internet arroja la pantalla de error ("Sin conexión").
2. Orientada a Servicios (API + SPA) ❌ Inestable Desacoplamiento limpio, comunicación eficiente por JSON. Si el técnico recarga la página o se cierra la pestaña sin red, la app no puede recargarse sin Service Worker.
3. App Nativa (Kotlin + Swift) ✅ Excelente offline Rendimiento máximo, acceso total al hardware y sensores. Duplica el costo de desarrollo (dos equipos especializados), pago de licencias de desarrollador y fricción en tiendas.
4. Multiplataforma (Flutter / RN) ✅ Buen offline Un solo código base para Android e iOS, interfaz fluida. Instaladores muy pesados (40 a 70 MB) y dependencia de empaquetado y firmas de certificados para distribución.
5. Web Progresiva (PWA) ✅ Excelente offline Capacidad offline mediante Service Worker e IndexedDB, peso inferior a 2 MB, instalación directa sin tiendas. Sujeta a políticas de almacenamiento de navegadores (mitigables mediante diseño de arquitectura).

2. Entregable Parcial 2: Compatibilidad y Requerimientos de Instalación

2.1. Mapeo de Navegadores y Limitaciones Específicas

Se investigaron los motores dominantes en los dispositivos móviles que portan los técnicos de campo:

  • Chromium-Based (Google Chrome, Edge, Samsung Internet en Android): Representa el entorno más maduro para PWAs. Genera automáticamente un paquete WebAPK que integra la app en el cajón de aplicaciones de Android, soporta el evento beforeinstallprompt para disparar banners de instalación personalizados, permite cuotas de almacenamiento de varios Gigabytes y soporta la API de Sincronización en Segundo Plano (Background Sync API).
  • WebKit / Safari (Apple iOS en iPhone / iPad): Posee limitaciones concretas que deben ser gestionadas por la arquitectura:
    1. Ausencia de evento de instalación programática: No existe beforeinstallprompt; la instalación debe ser guiada manualmente al usuario (Pulsar botón Compartir -> "Añadir a pantalla de inicio").
    2. Política de Desalojo de Datos (ITP 7-Day Cap): Si la PWA no ha sido agregada a la pantalla de inicio y no se abre en 7 días, Safari puede purgar la caché y el almacenamiento local. Una vez agregada al Home Screen, la persistencia se estabiliza.
    3. Cuota Inicial de Almacenamiento: Límite más restrictivo por origen (inicialmente 50 MB, ampliable bajo solicitud al sistema).
    4. Background Sync no implementado: Se requiere implementar un fallback escuchando el evento nativo window.addEventListener('online', ...) cuando la aplicación esté en primer plano.

3. Entregable Parcial 3: Preparación del Entorno y API REST Base

3.1. Arquitectura del Entorno de Desarrollo

Se implementó un entorno de desarrollo profesional basado en estándares nativos de Node.js (v24.x LTS) sin dependencias pesadas:

  • Servidor HTTP y API REST (`server.js`): Implementado con módulos nativos (node:http, node:fs, node:path, node:url). Garantiza cero fricción de instalación, arranque instantáneo y portabilidad completa.
  • Persistencia de Datos (`data/reportes.json`): Sistema de almacenamiento en archivo JSON que simula la base de datos central de la empresa. Cada reporte cuenta con folio consecutivo (ej. REP-2026-001), cliente, tipo de equipo, prioridad, falla y fecha.
  • Encabezados CORS y Tipado MIME: Soporte completo para peticiones entre dominios cruzados (CORS) y servicio de estáticos con tipos MIME estrictos.

3.2. Endpoints de la API REST Implementados

  • GET /api/health: Verifica el estado del servicio y métricas de tiempo de actividad (*uptime*).
  • GET /api/reportes: Devuelve la colección completa de reportes guardados en formato JSON.
  • POST /api/reportes: Recibe un nuevo reporte en JSON, valida los campos obligatorios, asigna un folio correlativo y lo persiste en disco.
  • DELETE /api/reportes/:id: Permite depurar o eliminar registros de prueba.

3.3. Configuración de Túnel Seguro HTTPS para Pruebas en Smartphones

Para validar el comportamiento en teléfonos móviles reales (Android y iPhone) y cumplir con el requerimiento ineludible de HTTPS, se configuró la exposición del puerto local 3000 mediante túneles seguros: 

# Opción 1: LocalTunnel (Directo con NPX)
npx localtunnel --port 3000

# Opción 2: Ngrok
ngrok http 3000
